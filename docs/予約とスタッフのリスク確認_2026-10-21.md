- 保存データの照合、予約処理単体、通信順序の模擬、実際の同時HTTP通信、Chrome画面操作を分けて確認した。

## 見つけて修正した内容

| リスク | 修正・検査 |
| --- | --- |
| 同じ再送キーで入力・本人が変わり、以前の結果が返る | 入力とログイン会員を照合。同一内容だけ再送扱い。違う入力・旧形式は拒否し、結果のID・トークンを返さない |
| 人数の負数・小数、存在しない日付 | 整数1〜3名・実在日・台帳の0〜27時を確認 |

| 日時変更中に元予約開始や回数券期限をまたぐ | 受付時刻を処理全体で共有し、一部だけ更新される状態を防止 |
| 外部予約の取消後に担当行が残る | 取消時に担当行も解除。再送で増減しないことを確認 |

| 別日置き場の札が古く、違う内容を承認してしまう | 確認前に元予約を読み直す。変更・取消・移動済みなら札だけ解除し、予約を上書きしない |

## 確認結果

- 予約処理32項目、通信・置き場・表示29項目を通過。通常予約、同内容の再送、複数名、スキル変更、指名確認、回数券残1回、日時変更失敗時の原状保持、取消再送、境界時刻を含む。
- HTTP検査5項目を通過。同じ予約20回の同時送信は1件だけ成立。別キーで同じ担当・時間は拒否。同じキーで氏名・宛先・時刻を変更した3件も拒否。2予約の同じ枠への同時移動は1件成功・1件拒否で、保存後も重複なし。
- Chromeで指名なし予約を作成し、台帳に1件だけ反映することを確認。大水から中山へ14時→15時にドラッグし、さらに別日置き場から翌日の大水へ移動。確認画面の日時・担当と保存後の枠が一致し、置き場の札も解除された。
- スマホ幅390×844で詳細画面の候補を選び、同じ予約を中山の16〜17時へ移動。確認画面と保存後の担当・時間が一致した。新規予約通知が操作欄に重なるときは、通知を閉じてから操作した。星印の表示は実際の画面・要素とも各スタッフ1個で、繰り返し描画しても増えないことを確認した。

## 検査の限界

- 同時操作は本番と同じ1台・1プロセス構成で検査。複数の本番サーバーを同時起動する構成には対応させていない。
- 停電・ディスク故障・OS強制終了・本物のメール配信障害は発生させていない。既存の保存と復旧手順は別途維持する。
- 通信遅延・応答順・失敗は模擬検査を含む。すべての端末やネットワーク状態を網羅した保証ではない。
- iPhone実機の長押しやPeakManagerとのアニメーションの完全一致は今回の追加検査の対象外。
